## 5. Constats nouveaux

### 🟠 Moyens — à traiter **avant d'activer `DATABASE_URL` en production**

**M1. Le `POST` accepte n'importe quel `subjectId` — croissance illimitée de la table.**
Aucune validation contre le catalogue (testé : un `subjectId` de **4 000 caractères** accepté), aucune limite de longueur, aucun rate-limit. Chaque POST sans cookie crée une nouvelle session. **Démonstration : 63 lignes / 62 sessions créées en quelques secondes** depuis un simple script. Sans base, l'impact est nul (réponse `local_only` honnête) ; avec une base Neon/Supabase facturée, n'importe qui peut gonfler la table indéfiniment.
*Correctif (~30 min) : rejeter tout `subjectId` absent du catalogue (le catalogue est statique côté serveur) + statut invalide → 400.*

**M2. Un statut invalide écrase silencieusement un statut valide.**
`POST {"subjectId":"dj","status":"nimportequoi"}` ne renvoie pas d'erreur : il **réinitialise** `dj` de `chosen` à `interested` (vérifié en base). Un client buggé (ou un appel accidentel) dégrade l'état utilisateur sans signal.
*Correctif : 400 sur statut hors `{interested, contacted, chosen}` au lieu du repli silencieux.*

**M3. La fusion local/serveur fait toujours gagner `localStorage`.**
Au chargement : `{...fromServer, ...local, ...current}`. Conséquence concrète : un élément **retiré depuis un autre navigateur ressuscite** sur celui-ci (le serveur dit « supprimé », le cache local périmé dit « présent », et le local gagne). La persistance multi-appareils promise par le README fonctionne à l'ajout, mais casse à la suppression. À défaut de changer la politique, il faut au minimum documenter le comportement ; idéalement : dernière écriture gagnante par clé, ou serveur autoritaire.

**M4. 26/36 couvertures + les visuels hero/fermeture sont toujours en hotlink Pexels.**
29 URLs Pexels dans le HTML servi (8 images uniques réutilisées en boucle). Le README le reconnaît honnêtement — reste que c'est : une dépendance de disponibilité externe, zéro optimisation (`background-image` CSS, jamais `next/image`, pas de `sizes`/SRCSET), et des conditions d'usage Pexels à valider avant tout usage commercial.

### 🟡 Mineurs

| # | Constat |
|---|---|
| m1 | **A11Y — dialogues incomplets** : la fiche sujet et le drawer `role="dialog"` n'ont ni piège de focus, ni fermeture par `Échap`, ni déplacement du focus à l'ouverture, ni restitution du focus à la fermeture. Le toast n'a pas `role="status"`/`aria-live` (invisible aux lecteurs d'écran). |
| m2 | **9 images mortes** (`public/covers/111–119`, **2,0 Mo**) référencées nulle part mais livrées et servies publiquement. |
| m3 | **3 classes CSS orphelines** : `plan-block`, `selected-section`, `suggestion-section` (0 règle dans `globals.css`). |
| m4 | **Tailwind 4 installé mais inutilisé** : 0 classe utilitaire dans le JSX. Seul le preflight (reset) du `@import "tailwindcss"` est effectivement utile. Poids de build et risque de divergence pour rien — soit l'assumer explicitement, soit le retirer (en réintégrant le reset nécessaire). |
| m5 | **favicon 404**, pas de `robots.txt`, pas de métadonnées Open Graph / Twitter (le titre et la description existent, c'est déjà ça). |
| m6 | **`Cache-Control: public, max-age=0`** sur `/covers/*.jpg` (157–173 Ko chacune) : le navigateur revalide à chaque visite. L'edge Vercel atténue, mais un `max-age` long serait gratuit. |
| m7 | `GET /api/wedding/selections` **sans cookie** renvoie `persistence:"server"` même quand la base est injoignable (le code court-circuite avant de tester la base). Cosmétique, mais trompeur pour le diagnostic. |
| m8 | Colonne `sort_order` **jamais lue ni écrite** par l'application. |
| m9 | Script `test` fragile : `src/**/*.test.ts` ne matche qu'un seul niveau de répertoire en `sh` (aucun globstar). Ajouter un test à la racine de `src/` et il ne sera pas exécuté. |
| m10 | `statusLabel` exporté et jamais importé (reliquat du nettoyage). |
| m11 | Aucun en-tête de sécurité (CSP, `X-Frame-Options`, `Referrer-Policy`) dans `next.config.ts`. Faible risque pour une vitrine statique, gratuit à ajouter. |
| m12 | Cookie `Secure` + test local : en `NODE_ENV=production` sur `http://localhost`, un vrai navigateur refusera le cookie `Secure` — dérouterait quiconque teste la persistance en local. (Sans impact sur Vercel/HTTPS.) |
| m13 | 90 relations asymétriques sur ~180 liens (A→B sans B→A). Sans doute voulu (liens éditoriaux), à confirmer. |

### 🟢 Ce qui est solide

- **Qualité de livraison** : lint, typecheck, 10 tests, build — tout est vert et **reproductible** (lockfile commité, versions épinglées à l'exacte, `engines` déclaré).
- **Dégradation en cascade honnête et testée** sur les 3 états (sans base / base down / base OK). La promesse « le site marche toujours, seule la persistance varie » est tenue.
- **Persistance serveur validée de bout en bout** (première fois) : migration propre sur PostgreSQL 18.4, PK `(session_id, subject_id)` correcte, requêtes 100 % paramétrées via Drizzle (**aucune injection SQL possible**), cookie correctement durci (`HttpOnly`, `SameSite=lax` couvre le CSRF sur les POST cross-site, `Secure` en prod).
- **Performance de la page `/`** : statique, pré-rendue intégralement (36 cartes dans le HTML), 35,4 Ko de HTML, ~202 Ko de JS gzippé, TTFB local < 25 ms.
- **Le moteur de projet** (`sortWeddingSelectionsByMoment`) : pur, mémoïsé, bien testé, immuable — le meilleur code du dépôt.
- **Direction artistique** : CSS éditorial dense et cohérent, 2 breakpoints (860/400 px) réellement travaillés, `:focus-visible` stylé, `lang="fr"`, `aria-label` systématiques.
- **Intégrité du catalogue** : 0 orphelin, 0 doublon, 19 univers, contenu rédigé (pas de lorem ipsum).
- **Documentation à jour** : le README décrit exactement le comportement observé (chose rare).
